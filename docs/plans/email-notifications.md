## 1. 기존 코드에서 확인한 사실

| 영역 | 현재 구현 | 설계에 미치는 영향 |
| --- | --- | --- |
| 서버 | Node.js 24, Fastify 5, Prisma 6, MySQL | 기존 서버에 application/domain/infrastructure 구조로 확장 가능 |
| 클라이언트 | Next.js 15, 별도 서버로 `/api` 프록시 | 이메일 생성·예약은 서버에 두고 관리 UI만 클라이언트에 추가 |
| 공시 | 관리자 등록 즉시 공개. 생성·수정은 같은 함수에서 분기하며 삭제 가능 | 생성 이벤트를 명시적으로 구분해야 한다. 현재 초안·예약 공개 상태는 없다 |
| 인증·이메일 | DataGSM 응답의 이메일을 서명 세션 쿠키에 보관. 투자·출금 의향서에도 당시 이메일을 저장 | 로그인 사용자 전체를 조회하는 User 테이블, 최신 연락처, 수신 설정은 없다 |
| 관리자 | 환경변수 `ADMIN_EMAILS` 또는 `ADMIN_EMAIL`로 권한 판단 | 기존 권한 판정을 발송 관리 화면에 재사용 |
| 보유확인서 | 관리자 페이지에서 현재 보유 종목을 읽고 `window.print()` 호출 | 이메일용 본문 템플릿과 발급 데이터 보존 기능이 필요 |
| 포트폴리오 이력 | 일별 합계·환율·마감값 저장. 종목별 시점 스냅샷은 없음 | 이번 확인서는 발송 시점의 최신 내역을 사용하므로 발송 원본 보존을 추가하면 된다 |
| 실배당 | 관리자가 배당월과 실배당 합계를 입력. 해당 월말 평가액 확정이 저장의 선행조건 | 1일에 자동으로 실배당금이 준비된다고 가정할 수 없다 |
| 지급액 계산 | 완료 투자 의향은 다음 달부터 포함하고 완료 출금은 해당 월부터 FIFO 차감 | 이미 있는 원금 대상 선정·배분 함수를 재사용할 수 있다 |
| 계산 단위 | 관리자 UI는 투자 의향서 한 건을 선택해 계산 | 개인 이메일을 보내려면 동일 `userId`의 여러 의향을 합산해야 한다 |
| 계산 확정성 | 개인별 지급 내역·승인·송금 기록 없음. 정책 문서에서도 참고 계산값으로 정의 | 이메일을 실제 지급 완료나 승인된 확정 금액으로 표현할 근거가 없다 |
| 계산 시점 | 배분 계산의 `V`는 현재 평가액. 월별 레코드의 월말 평가액은 수익률 참조용 | 월말 평가액을 배분에 적용하는 것은 별도 정책 변경이다 |
| 금액 정밀도 | 배분 함수는 소수 계산, 화면은 `Math.round`로 원 단위 표시 | 개인별 반올림 합과 전체 반올림 합의 차이를 처리할 정책이 없다 |
| 의향 이력 | 현재 상태와 `updatedAt`을 완료 시점처럼 사용하며 상태 변경·철회 가능 | 후일 재계산 시 과거 계산 대상이 달라질 수 있어 발송 입력을 보존해야 한다 |
| 스케줄러 | `node-cron`, `Asia/Seoul`, MySQL named lock, 시작 시 일부 작업 보충 실행 | 실행 기반을 재사용하되 이메일은 기간별 완료 여부를 영속화해야 한다 |
| 배포 | 서버는 Docker 컨테이너, 클라이언트는 별도 배포. 서버 이미지에 클라이언트 파일 없음 | 이메일 템플릿은 서버에 배포. 서명 이미지 포함 여부·제공 방식은 별도 검토 |
| DB 배포 | 추적된 Prisma migration SQL 없음. 배포 훅은 기존 테이블 rename 스크립트를 호출 | 새 테이블·컬럼을 배포하는 경로와 기존 DB 기준선 확인이 필요 |

## 2. 확정된 요구와 설계 기본안

인터뷰에서 확정한 항목은 아래에 기록한다. 추가 선택이 없었던 세부 동작은 기존 구현과 요청 범위를 기준으로 기본안을 제시한다.

### 확정 사항

- 매월 1일 지급액 안내는 각 투자자에게 본인의 지급액만 전송한다. 관리자에게 전체 지급 내역을 이메일로 보내는 것은 이번 선택에 포함되지 않는다.
- 안내 금액은 직전 달의 실제 배당을 기준으로 계산한다. 예: 10월 1일 안내에는 9월 실배당과 9월 배당 적격 잔액으로 계산한 개인별 금액을 사용한다. 당월 예상 배당을 사용하지 않는다.
- 1일 작업 실행 시 전월 실배당이 입력되지 않았으면 발송을 보류한다. 입력 완료 후 계산에 필요한 데이터가 준비되면 별도 발송 승인 없이 자동 발송한다. 투자자에게 미확정 대기 안내 메일은 보내지 않는다.
- 해당 배당월의 계산 대상 투자자는 계산 결과가 0원이어도 개인별 금액 안내를 받는다. 실배당 미입력은 0원으로 취급하지 않는다.
- 신규 공시 이메일은 현재 투자 잔액이 있는 투자자에게 보낸다. 사용자별 완료 투자 의향 금액 합계에서 완료 출금 의향 금액 합계를 차감한 값이 0원보다 큰 경우를 대상으로 한다.
- 분기 보유확인서는 이메일 본문으로 전달한다. 확인서 내용을 HTML 본문에 담으며 PDF 첨부·다운로드 방식은 구현 범위에서 제외한다.
- 분기 보유확인서는 발송 당시의 최신 보유 내역을 기준으로 한다. 분기말 과거 내역을 재구성하는 방식은 사용하지 않는다.
- 분기 보유확인서 발송일은 매년 1월 1일·4월 1일·7월 1일·10월 1일이다.
- 정기 메일의 특정 발송 시각은 지정하지 않는다. 한국시간 기준 해당 날짜부터 발송 가능하며, 실행 시 데이터가 준비되어 있으면 발송한다. 공시는 등록 후, 늦게 입력된 실배당 안내는 데이터 준비 후 처리한다.
- 발송 수단은 사용자가 제공한 SMTP 서버 `mail.kimtaeeun.site:465`(SSL/TLS), 인증 계정 `contact@kimtaeeun.site`를 사용한다. 비밀번호는 구현·연결 검증에 필요한 시점에 사용자가 별도로 입력한다.
- 투자자의 수신 주소는 DataGSM 로그인 이메일을 사용한다. 별도 알림용 이메일 입력·변경 기능은 제공하지 않는다.
- 별도 수신 설정 없이 각 알림의 대상 조건을 충족하는 투자자에게 자동 발송한다. 종류별 수신 토글·구독 설정 화면과 API는 제공하지 않는다.

- 후속 정리: 임시 테스트 발송 화면·API·샘플·임의 지급액 계산을 코드에서 제거한다. 기존 TEST 이력은 보존하고 운영 발송기는 PRODUCTION만 처리한다.
- 메일 발송 이력은 `/admin`의 섹션 패널로 통합한다. 모드 선택·일정 안내 카드를 제거하고 상세·정정·재시도는 기존 어드민과 같은 모달에서 처리한다.
- 새 공시의 이메일 제목과 본문 제목은 공시 제목 그대로 사용한다. `NXDI 새 공시 · ` 접두어를 추가하지 않는다.

### 발송 동작 요약

| 종류 | 시작 조건 | 수신자 | 내용 |
| --- | --- | --- | --- |
| 신규 공시 | 등록 트랜잭션 완료 | 등록 시점의 투자 잔액 보유자 | 공시 제목·본문·등록 시각·상세 링크 |
| 월별 지급액 | 매월 1일 이후 전월 데이터 준비 완료 | 전월 배당 적격 잔액이 있는 투자자 | 본인의 전월 기준 계산액, 0원 포함 |
| 분기 확인서 | 1·4·7·10월 1일 이후 해당 회차 최초 준비 | 현재 투자 잔액 보유자라는 기본안 | 준비 시점 최신 운영종목 보유 내역을 이메일 본문으로 제공 |

### 추가 선택이 없었던 항목의 기본안

아래는 사용자에게 확정 답변을 받은 항목이 아니라 구현 계획의 제안이다.

- **분기 수신자:** 공시와 같은 현재 투자 잔액 보유자를 최초 발송 준비 시 확정한다. 펀드의 기존 운영종목 보유확인서를 이메일 형태로 제공한다.
- **기존 계산 유지:** 현재 평가액·다음 달 투자 적격·해당 월 출금 FIFO·기존 배분 정책을 유지한다. 사용자별 소수 계산액을 합산한 뒤 기존 `Math.round` 방식으로 한 번 표시하며 계산 원본을 함께 저장한다. 반올림 전 합계와 표시 금액 합계의 차이를 별도 기록하고 이를 임의의 투자자에게 재배분하지 않는다. 실제 송금·회계 정산을 새로 구현하지 않는다.
- **공시 수정·삭제:** 최초 등록만 자동 발송한다. 공시가 수정되면 아직 어떤 수신자에게도 전송을 시작하지 않은 경우에 한해 원본 버전을 갱신한다. 한 명이라도 전송을 시작하면 그 회차 내용은 고정한다. 삭제 시 미전송 항목은 취소한다. 발송 후 정정은 새 공시 또는 별도 정정 버전을 사용한다.
- **월별 정정:** 최초 발송을 시작한 금액은 변경 입력만으로 자동 재발송하지 않는다. 관리자가 미리보기 후 명시적으로 정정 발송을 실행하며 정정 사유·버전을 저장한다.
- **발신자:** `NXDI <contact@kimtaeeun.site>`를 사용하고 답장은 같은 계정에서 받는다.
- **운영 상태:** 미입력·연락처 오류·실패·결과 불명은 관리자 화면에 표시한다. 운영 오류 이메일과 IMAP 반송 수집은 1차 범위에 포함하지 않는다.
- **기존 수신자 전환:** 사용자별 저장 이메일이 하나로 일치하면 기존 의향서에서 초기 연락처를 가져온다. 충돌하면 재로그인 확인 필요 상태로 남긴다. OAuth에서 다시 확인한 주소가 우선한다.
- **보관:** 발송 원본·이력과 중복 방지 키는 1차 버전에서 자동 삭제하지 않는다. 실제 데이터 규모를 확인해 후속 보관 정책을 정한다.

## 3. 제안하는 공통 구조

```text
공시 등록 / 월별 안내 준비 / 분기 문서 발급
  -> 업무 데이터와 발송 이벤트를 같은 DB 트랜잭션에 기록
  -> 대상자 확정 및 수신자별 발송 항목 생성
  -> 기존 서버의 발송 작업이 대기 항목을 가져옴
  -> MailSender 인터페이스의 SMTP 어댑터로 전송
  -> 접수 결과·재시도·실패 이력 저장
```

처음에는 기존 MySQL과 서버 스케줄러를 사용한다. 별도 큐 서비스 추가 여부는 예상 규모와 운영 요구가 확인된 뒤 판단한다. 공시 등록 요청이 SMTP 서버의 응답을 기다리지 않도록 한다.

### 실행 시점과 누락 복구

- 사용자 지정 시각 없이 기존 스케줄러에서 1분 간격으로 발송 가능 작업을 확인하는 구현안을 사용한다. 달력 날짜 판단은 `Asia/Seoul`로 하고 예정 날짜의 00:00은 발송 가능 시작점으로만 사용한다.
- 서버 시작 시에도 같은 준비 서비스를 호출한다. 달력 경계의 cron 한 번에만 의존하지 않는다. 공시 등록·실배당 저장 직후에는 처리기를 깨울 수 있지만 DB 예약 항목이 복구 기준이다.
- 업무 키는 `disclosure:<id>:<revision>`, `monthly:<YYYY-MM>:<revision>`, `quarterly:<YYYY-Qn>:<revision>`을 사용한다. 회차당 사용자 ID별 전송 항목을 하나만 생성한다.
- 알림 서버 최초 시작 시각을 `NotificationControl.activatedAt`에 한 번 저장하고 그 이후 도래한 날짜·생성된 공시만 자동 대상에 포함한다. 최초 시작 이전 공시나 배당월은 자동 소급 전송하지 않으며 재시작으로 기준을 초기화하지 않는다. 과거 데이터를 테스트하려고 이 기준을 바꾸지 않는다.
- 월별 미입력은 해당 귀속월을 유지한 채 준비될 때까지 보류한다. 분기 확인서는 해당 분기 안에 재기동하면 최신 내역으로 보충하되, 다음 분기가 지난 미생성 회차는 `SKIPPED`로 표시하는 기본안이다. 생성된 원본의 전송 재시도는 별도 상태로 관리한다.
- 수신자가 없으면 회차를 `NO_RECIPIENTS`로 종료한다. 이후 투자한 사람에게 이미 종료한 회차를 뒤늦게 발송하지 않는다.

### SMTP 연결 설계

사용자 제공 연결 정보와 구현 제안을 구분한다. 아래 여섯 값은 모두 필수 설정이며 실제 SMTP 접속·인증·발송은 아직 검증하지 않았다.

| 설정 | 값 / 상태 |
| --- | --- |
| `SMTP_HOST` | `mail.kimtaeeun.site` — 사용자 제공 |
| `SMTP_PORT` | `465` — 사용자 제공 |
| `SMTP_SECURE` | `true` — 연결 시작부터 TLS 사용 |
| `SMTP_USER` | `contact@kimtaeeun.site` — 사용자 제공 |
| `SMTP_PASSWORD` | 사용자 후속 입력. 문서·저장소에 실제 값을 기록하지 않음 |
| `MAIL_FROM` | `NXDI <contact@kimtaeeun.site>` — 명시적으로 설정 |

- 구현 라이브러리는 Nodemailer SMTP transport를 제안한다. 포트 465에는 `secure: true`를 명시하고 TLS 인증서 검증을 유지한다. 연결 제한시간을 명시하며 운영 환경에서는 SMTP 원문 디버그 로그를 끈다. [Nodemailer SMTP 공식 문서](https://nodemailer.com/smtp)
- 새로 정의할 `MailSender` 인터페이스 뒤에 Nodemailer를 배치하고 라이브러리 버전은 구현 시 호환성을 확인해 lockfile에 고정한다. 한 발송 항목에는 수신자 한 명만 넣는다. 처음에는 낮은 동시성으로 시작하고 서버 제한을 확인한 뒤 조정한다.
- HTML 본문과 일반 텍스트 본문을 함께 전달한다. 전달 항목별 `Message-ID`를 저장해 서버 로그와 대조할 수 있게 한다. `Message-ID`가 같다는 이유만으로 중복 전송이 차단된다고 가정하지 않는다. [Nodemailer 메시지 설정](https://nodemailer.com/message)
- 사용자에게 받은 IMAP `mail.kimtaeeun.site:993` 설정은 메일 수신용이다. 현재 요구인 발송 기능에서는 메일함 읽기·IMAP 연동을 추가하지 않는다. 자동 반송 수집·배달 웹훅이 제공된다고 가정하지 않는다.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`은 모두 서버 시작의 필수 환경변수다. 값이 누락되거나 잘못되면 서버를 시작하지 않는다. 위 표의 예시 값은 런타임 기본값으로 대체되지 않는다. 비밀번호는 서버 시작 전에 비밀 환경변수로 주입하고 `.env.example`에는 빈 값만 기록한다. 클라이언트 환경변수·응답·로그에 노출하지 않는다.
- 정상적으로 시작된 서버는 운영 자동 발송 작업을 항상 실행한다. 운영 전 검증은 운영 투자자 연락처·발송 대기 항목이 없는 격리된 스테이징 DB에서 수행한다. 처리량·제한시간 설정인 `MAIL_BATCH_SIZE`, `SMTP_CONNECTION_TIMEOUT_MS`, `SMTP_SOCKET_TIMEOUT_MS`에는 기본값을 유지한다.
- 구현 후 비밀번호를 입력받으면 먼저 `verify()`로 연결·TLS·인증을 검사할 수 있다. 이 검사는 메시지를 전송하지 않으며 실제 발신 주소 허용이나 받은편지함 도착을 입증하지는 않는다. 이후 사용자 지시 범위의 테스트 수신자로 실제 전송을 확인한다. [연결 검증 범위](https://nodemailer.com/smtp#verifying-the-configuration)
- 메일 서비스 장애를 DB readiness 검사에 결합하지 않는다. 메일 기능 상태는 관리자 화면과 작업 상태에서 별도로 보여준다.

### 책임 분리

- `domain`: 수신 대상 판정, 기간 계산, 개인별 배분 합산·원 단위 정책, 발송 상태 전이.
- `application`: 공시 알림 예약, 월별 안내 준비, 분기 확인서 발급, 테스트 입력 계산·미리보기·발송, 발송 처리, 재시도.
- `infrastructure`: Prisma 저장소, SMTP 어댑터, 이메일 HTML·텍스트 템플릿 렌더러. PDF 렌더러·문서 파일 저장소는 추가하지 않는다.
- `scheduler`: 예정 시점 확인, 미처리 기간 보충, 준비 완료 항목 전송.
- `routes`: 관리자의 발송 이력·미리보기·결과 확인·재시도 경로를 제공. 사용자 수신 설정 경로는 추가하지 않는다.

### 저장 모델 초안

다음 모델을 구현 기준으로 제안한다. 새 테이블은 저장소의 `tb_` 이름 규칙을 따른다. 시간은 UTC로 저장하고 기간 문자열만 KST 달력을 기준으로 생성한다.

| 모델 | 역할 | 주요 데이터·제약 |
| --- | --- | --- |
| `NotificationRecipient` | 지속적으로 관리하는 수신자 | DataGSM 사용자 ID unique, DataGSM 이메일, 주소 출처·마지막 확인 시각, 주소 버전, 연락처 오류 상태. 구독·수신 설정 필드는 추가하지 않음 |
| `NotificationEvent` | 한 공시 또는 한 기간의 발송 계기 | 종류, `mode`(PRODUCTION/TEST), 업무 식별자, 기간, 정정 버전, 예정 시각, 고정된 콘텐츠 참조, 대상 확정 상태. 업무 키에 unique. 과거 TEST 원본은 감사용으로 보존하고 새 TEST 기록을 생성하지 않음 |
| `EmailDelivery` | 수신자별 처리 단위 | 이벤트·수신자 unique, 수신 주소 스냅샷, 상태, 시도 수, 다음 시도 시각, claim 만료, SMTP Message-ID·접수 응답 코드·가능한 경우 서버 큐 ID, 오류 코드 |
| `EmailDeliveryAttempt` | 실제 전송 시도 원본 | delivery ID·시도 번호 unique, 실제 수신 주소·주소 버전, 시작·완료 시각, 전송 단계, 접수 응답·오류 코드. 재시도 시 이전 주소·결과를 덮어쓰지 않음 |
| `QuarterlyStatement` | 분기 확인서 원본 | 분기, 실제 데이터 기준 시각, 발급 시각·번호, 종목별 데이터, 환율·가격 기준, 템플릿 버전, HTML·텍스트 본문, 원본 데이터 지문 |
| `MonthlyPayoutNotice` | 월별 안내에 사용한 계산 원본 | 귀속월·안내일, 실배당 `recordId`·`updatedAt`·입력 지문, 계산에 쓴 평가액·기준 시각, 대상 의향 입력, 정책값·버전, 사용자별 계산액, 정정 번호 |

이벤트 준비 상태와 개별 전송 상태를 분리한다. 이벤트는 `WAITING_DATA / READY / COMPLETED / NO_RECIPIENTS / CANCELLED / SKIPPED`, 개별 전송은 `PENDING / CLAIMED / SUBMITTING / RETRY_WAIT / ACCEPTED / FAILED / UNKNOWN / CANCELLED`를 사용한다. 업무 키·수신자 중복 제약 외에 `(status, nextAttemptAt)`과 claim 만료 시각에 인덱스를 둔다. 내용 원본은 버전별 JSON·HTML·텍스트로 고정 보관할 수 있으며 개인별 데이터가 전체 수신자 본문에 섞이지 않게 조립한다.

과거 TEST 원본·전송 이력은 감사용으로 보존한다. 새 발송과 정정·재시도는 PRODUCTION만 허용하며, 이미 전송 중이던 과거 TEST의 만료 복구와 UNKNOWN 확인은 유지한다.

기존 공시·월별 실배당 삭제가 발송 이력을 연쇄 삭제하지 않게 한다. 참조 식별자와 원본을 남기거나 관계에 `SetNull`을 사용하며, 원본을 삭제해도 이미 발송한 내용을 조회할 수 있어야 한다. 현재 월별 실배당 모델에 별도 버전 필드는 없으므로 레코드 ID·수정 시각·입력 지문으로 안내의 원천을 식별한다.

SMTP 최종 접수 성공은 `ACCEPTED`로 기록한다. 실제 받은편지함 도착·열람 상태는 확인되지 않았으므로 이와 구분한다. 추가 상태 수집 경로를 구현하기 전에는 자동 반송·배달 완료 판정을 하지 않는다. SMTP 접수는 서버가 전달 책임을 인수하는 단계다. [RFC 5321 §4.2.5](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.2.5) 이메일 주소만으로 사용자 신원을 병합하지 않는다.

### 중복·실패 처리

1. 공시 생성과 이벤트 생성은 원자적으로 수행한다. 같은 트랜잭션에서 실패하면 둘 다 저장되지 않는다.
2. 공시 수신자 ID는 등록 트랜잭션에서 일관된 투자·출금 조회 결과로 고정한다. 분기 확인서는 최초 준비 시 확정한다. 재실행해도 unique 제약으로 중복 항목을 만들지 않는다. 별도 수신 주소 갱신은 대상 ID를 바꾸지 않는다.
3. 작업자는 만료 시각이 있는 claim으로 항목을 가져온다. 네트워크 전송 동안 긴 DB 트랜잭션을 유지하지 않는다.
4. 접수 전 명확한 연결 실패·일시 SMTP 거절은 지연 후 재시도한다. 인증·인증서·설정 오류는 설정 확인이 필요하며, 영구 거절·재시도 소진은 관리자 화면에서 처리한다. 어댑터는 Nodemailer의 `code`, `command`, `responseCode`를 이용해 분류하고 원문 응답은 민감값을 제거한 뒤 보관한다. [오류 구조](https://nodemailer.com/errors)
5. 본문 전송 후 최종 응답을 잃었거나 SMTP 접수 직후 로컬 성공 기록 전에 종료되면 `UNKNOWN`으로 남기고 무조건 재전송하지 않는다. 만료된 작업도 전송 단계에 따라 미접수 재시도와 결과 불명 처리를 구분한다. 관리자가 메일 서버 로그와 대조해 접수 확인 또는 재시도를 선택하는 구조를 제안한다. SMTP 최종 응답 대기 중 연결 문제는 중복 전송으로 이어질 수 있다. [RFC 5321 §4.5.3.2.6](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.2.6) DB unique나 `Message-ID`만으로 정확히 한 번 전송을 보장하지 않는다.
6. 전송 재시도는 동일 콘텐츠·동일 업무 버전을 사용한다. 금액이나 문서를 바꾸는 정정 발송은 새 버전으로 만든다.
7. 알림 서버 최초 시작 시각과 처리 기간을 저장하여 최초 배포가 모든 과거 공시·기간의 일괄 발송을 유발하지 않게 한다.
8. 종료 시 새 claim을 중단하고 진행 중 작업과 SMTP 연결을 정리한다. 강제 종료 후에는 claim 만료와 저장된 전송 단계에 따라 재시도 또는 결과 불명 상태로 복구한다.

## 4. 기능별 흐름

### 4.1 신규 공시

- 수신 범위 확정: 사용자별 `COMPLETED` 투자 금액 합계에서 `COMPLETED` 출금 금액 합계를 뺀 잔액이 0원보다 큰 투자자만 대상으로 한다. 대기·거절·철회 의향은 제외한다. 배당 대상 선정의 다음 달 적격 규칙은 공시 수신 조건에 적용하지 않는다.
- `upsertDisclosure`의 신규 생성 분기에서 이벤트를 함께 저장하도록 application 서비스와 트랜잭션 경계를 정리한다.
- 기본안으로 등록된 공시 ID·제목·등록 시각·본문·공개 링크를 발송 콘텐츠에 포함한다. 거래 내역이 있는 공시는 거래 정보도 구조화해 본문에 표시한다.
- 생성 당시 수신 대상 기준을 남기고 사용자별 개별 전송한다. 수신자 목록이 다른 사람에게 노출되는 단체 To/CC는 사용하지 않는다.
- 수정·삭제는 2절의 기본안을 적용한다. 공시 삭제 시 미전송 항목을 취소하고 이미 보낸 메일의 기록은 보존한다. 전송 시도 직전 원본의 취소 상태를 재확인하며 진행 중인 SMTP 전송의 회수는 보장하지 않는다.
- Markdown을 이메일 HTML로 변환할 경우 허용 태그·URL 처리와 일반 텍스트 본문을 함께 준비한다.

### 4.2 분기 보유확인서

- 발송일 확정: 매년 1·4·7·10월 1일. 특정 시각을 지정하지 않고 `Asia/Seoul` 기준 해당 날짜부터 데이터가 준비되는 대로 발송한다. 회차 식별자는 발송 예정일이 속한 연도·분기로 고정한다.
- 기존 서식의 대상은 펀드의 전체 운영종목이다. 요청의 보유확인서는 이 기존 ‘운영종목 보유확인서’를 활용하는 것으로 우선 해석한다. 개인 투자 원금·보유 지분을 증명하는 서식은 없다.
- 전달 형식 확정: 확인서 전체 내용을 이메일 본문에 넣는다. 종목명·보유 수량·기준가격·평가액 표와 총평가액·적용 환율·기준 일시·발급번호를 포함하는 구성을 제안한다.
- 펀드 공통 확인서라면 분기별 원본 데이터와 HTML·텍스트 본문을 한 번 생성하고 여러 수신자가 같은 내용을 받게 한다.
- 분기 시작일에는 월별 지급액 안내도 예정되어 있다. 두 안내는 별도 이벤트로 관리하여 전월 실배당 입력 지연이 보유확인서 발송을 막지 않도록 설계한다. 같은 메일로 합치는 기능은 현재 가정하지 않는다.
- 기준 확정: 발송 시점의 최신 보유 내역을 사용한다. 구현에서는 해당 회차의 최초 발송을 준비할 때 현재 포트폴리오를 한 번 조회해 종목명·수량·통화·가격·환율·평가액을 고정 저장하고 수신자 전체에 같은 원본을 사용한다.
- 발급 시각과 실제 가격·환율 데이터 관측 시각을 구분해 표시한다. 현재 저장값을 사용한다는 사실이 실시간 시장가격 확인을 뜻하지 않으므로 데이터 출처·갱신 상태를 확인한다.
- 발송 원본 생성 전 작업이 지연되면 실제 준비 시점의 최신 내역으로 생성한다. 원본 생성 후 발송 실패·재시작 시에는 저장된 원본을 재사용한다. 생성되지 않은 과거 분기는 3절의 누락 복구 기본안을 적용한다.
- 분기말 종목별 스냅샷 수집이나 과거 보유 내역 재구축은 이번 기능의 선행조건으로 추가하지 않는다.
- 발급번호·발급 시각·템플릿 버전·원본 데이터 지문과 완성된 본문을 저장하고 재시도 시 동일 내용을 사용한다. 현재 관리자 화면은 조회할 때마다 발급 시각과 지문이 달라지므로 발송 원본을 별도로 보존한다.
- 기존 화면의 인쇄 CSS와 브라우저 동작을 이메일에 옮기지 않고 이메일용 HTML 템플릿을 서버에서 작성한다. 단순한 표·인라인 스타일·시스템 글꼴을 사용하며 일반 텍스트 본문도 함께 제공한다.
- 좁은 화면에서 숫자·종목명이 읽히는지, 주요 메일 클라이언트에서 표가 유지되는지 검증한다. 첫 버전은 핵심 보유 정보·발급자·문서 식별자를 텍스트로 제공하고 서명·직인 이미지 삽입은 선택적 후속 개선으로 둔다.
- 확인서 제공을 위한 PDF 생성, 파일 저장소, 다운로드 API, 수신자의 관리자 페이지 접근은 필요하지 않다.
- 개인 투자 잔액 확인서 신규 제작은 이번 구현 범위에 포함하지 않는다.

### 4.3 매월 1일 지급액 안내

- 수신 범위 확정: 각 투자자에게 본인의 금액만 전송한다. 한 사용자의 여러 투자 의향은 합산해 한 통으로 안내하는 구조를 권장한다.
- 기준월 확정: 10월 1일 안내는 9월 실배당을 대상으로 한다. `dividendMonth`는 직전 달, `scheduledAt`은 다음 달 1일의 발송 예정 시각이다. 배당 적격 잔액도 `dividendMonth`로 계산한다. 늦게 발송해도 해당 안내의 기준월은 유지한다.
- ‘데이터 준비 확인 → 사용자별 계산 → 발송 원본 고정·예약 → 자동 발송’으로 책임을 나눈다. 별도 발송 승인 단계는 두지 않는다.
- `CalculateDividendPrincipalService`로 투자·출금 대상 잔액을 구하고 `userId`별 합산 후 서버의 `calculateDividendAllocation`을 적용한다.
- 현재 클라이언트에도 배분 공식이 중복되어 있다. 새로운 이메일 공식은 만들지 않고 서버 계산 결과를 기준으로 삼는다. 관리자의 이메일 미리보기도 같은 서버 결과를 표시한다.
- 배분에는 기존 코드·정책과 동일하게 최초 계산 시점의 현재 평가액을 사용한다는 기본안이다. 월말 평가액은 기존 실배당 저장 검증·수익률 참조 용도를 유지하며 배분 기준으로 자동 전환하지 않는다. 조회 기준·출처·실제 사용 값을 계산 원본에 저장한다.
- `MonthlyDividendRecord` 존재 여부와 실배당 0원을 구분한다. 미입력, 월말 기록 미확정, 평가 데이터 불가, 대상자 없음은 서로 다른 준비 상태다.
- 0원 안내 확정: 해당 배당월의 적격 잔액이 있는 투자자는 실배당 입력 후 계산 결과가 0원이더라도 금액 안내를 받는다. 실배당 미입력으로 계산할 수 없는 경우는 보류하며, 해당 월 배당 대상 자체가 없는 사람에게 0원 메일을 보내는 것으로 확대하지 않는다.
- 미입력 처리 확정: 실배당 입력이 늦으면 금액 안내를 보류하고, 입력이 완료되어 계산에 필요한 데이터가 준비되면 자동 발송한다. 투자자에게 미확정 안내는 보내지 않는다. 다음 달 1일 이전의 기록은 발송 가능 날짜까지 기다린다.
- 구현 제안: 실배당 저장 후 준비된 안내를 확인하고, 예약 작업에서도 미처리 기간을 재확인해 저장 직후 서버 종료·월 경과에도 누락을 복구한다. 늦게 입력된 기록은 원래 배당월의 안내로 처리하며, 이미 보낸 버전은 일반 입력 수정으로 자동 재발송하지 않는다. 정정은 새 버전·명시적 관리자 행위로 처리한다.
- 미입력·준비 실패는 관리자 화면에 표시한다는 기본안이다. 운영 알림 이메일은 추가하지 않는다.
- 사용자별 소수 계산액을 합산한 뒤 원 단위로 반올림하고, 반올림 차이는 메타데이터로 보존하는 기본안이다. 관리자 미리보기의 안내 총액은 개인별 표시액의 합으로 계산한다. 원 배분 풀과의 차이를 회사 보유분·재투자금 등에 임의 가산하지 않는다.
- 현재 상태와 `updatedAt`으로 과거 대상을 다시 계산하면 결과가 달라질 수 있다. 적어도 발송에 사용한 입력·결과는 고정 보존한다. 과거 시점의 원장 재구성이 요구되면 별도 완료 시각·상태 이력까지 범위를 확장한다.
- 미확정 계산을 지급 완료로 안내하지 않는다. 실제 승인 금액이나 세후 지급액이 요구되면 승인 원장·외부 확정액 입력 등 추가 데이터가 필요하다.

### 4.4 임시 테스트 기능 제거

초기 구현 확인에 사용한 테스트 발송은 후속 정리에서 제거한다. 테스트 화면·API·샘플·임의 금액 계산·고정 수신자·추가 전송 모드 주입 경로와 해당 전용 테스트를 삭제하며 환경변수 비활성화 방식으로 남기지 않는다.

기존 TEST 이력과 원본은 삭제하지 않는다. 새 발송 작업자는 PRODUCTION만 가져오고 구버전 TEST claim도 SMTP 시도 전에 거절한다. 상세·UNKNOWN 확인 API는 감사용으로 유지하지만 운영 화면에서는 PRODUCTION 이력만 표시한다. 제거 후 배포는 [운영 문서](../email-notification-operations.md#임시-테스트-기능-제거-후-배포)를 따른다.

## 5. 수신자·관리 화면

- 수신 주소 확정: DataGSM 인증에서 받은 이메일을 사용한다. OAuth 성공 시 안정적인 `user.id`를 기준으로 연락처를 저장·갱신하는 구조를 제안한다. 연락처 저장과 실제 수신 대상 판정은 분리하므로 로그인만으로 투자자 알림 대상이 되지는 않는다.
- 기존 투자·출금 의향서의 이메일도 작성 당시 DataGSM 세션에서 가져온 값이다. 초기 전환 시 사용자별 후보를 추출하고 출처·확인 시점을 남긴다. 서로 다른 주소가 남아 있는 사용자는 명확한 우선순위 또는 재로그인 확인으로 해소한다. 상태 변경용 `updatedAt`을 주소 확인 시각으로 취급하지 않는다.
- 새로 로그인한 DataGSM 응답의 주소가 이전 의향서 주소보다 우선한다. 발송 직전 최신 연락처를 확인하고, 실제 전송을 시도한 주소는 발송 시도 기록에 고정한다. 명확히 미접수인 대기 항목의 주소 변경은 반영하되 `ACCEPTED`·`UNKNOWN` 항목을 새 주소로 자동 재발송하지 않는다.
- 공시는 등록 시 투자 잔액이 0원인 사람과 전액 출금 완료자를 제외한다. 분기 확인서도 같은 잔액 조건을 최초 준비 시 적용하는 기본안이다. 월별 안내는 현재 잔액 대신 귀속월의 배당 적격 잔액을 사용한다.
- 별도 수신 이메일 입력 폼·변경 API·인증 메일 발송 기능은 추가하지 않는다. DataGSM 응답의 이메일 형식을 검사하고, 비어 있거나 사용할 수 없는 주소는 관리자에게 연락처 확인 필요 상태로 표시한다. 현재 응답 타입에 `email_verified`가 없으므로 별도로 확인된 주소라고 기록하지 않는다.
- 수신 방식 확정: 별도 수신 설정 없이 각 유형의 대상 조건을 만족하는 투자자에게 자동 발송한다. 사용자용 구독 토글·수신 해제 화면·설정 API를 추가하지 않는다.
- 관리자에게 발송 예정·준비 미완료·실패·결과 불명 항목과 미리보기·재시도를 제공한다. `/admin#admin-notifications`의 패널에서 종류·기간·상태로 조회하고 상세 모달에서 본문·시도·정정·결과 확인을 처리한다. SMTP 서버에서 접수한 항목의 재발송은 일반 재시도와 구분한다.
- 이력·개인 금액·저장된 발송 본문 접근은 해당 사용자 또는 관리자 권한으로 제한한다. 공급자 비밀키, 전체 본문·연락처·계좌번호를 일반 로그에 남기지 않는다.
- 수신 설정과 별개로 연락처 형식 오류·명확한 SMTP 영구 거절 등 기술적 실패는 기록하고 반복 전송을 중단한다. 자동 반송 수집은 이번 범위에 없으며, 외부에서 확인된 반송을 처리한다면 그 확인 근거를 남긴다.

## 6. 구현 순서 제안

1. **DB·연락처 기반:** 기존 DB와 migration 이력의 기준선을 확인하고 새 모델·중복 방지 제약을 추가한다. OAuth 연락처 갱신과 기존 투자자의 주소 후보 전환을 구현한다.
2. **발송 기반:** SMTP 어댑터·필수 비밀 환경변수·발송 대기열·시도 이력·재시도·결과 불명 처리·최초 시작 기준을 구현한다. SMTP 대역으로 application 로직부터 검증한다.
3. **신규 공시:** 생성 트랜잭션에서 이벤트·수신자 ID를 저장하고 HTML·텍스트 본문을 작성한다. 수정·삭제와 중복 등록 처리 범위를 검증한다.
4. **월별 지급액:** 기존 적격성·FIFO·배분 함수를 연결한 사용자별 집계, 원본 보관, 0원 안내, 미입력 후 자동 발송·재시작 복구를 구현한다.
5. **분기 확인서:** 최초 준비 시 최신 포트폴리오를 고정하고 이메일용 표를 생성한다. 월별 지급액과 별도로 준비·전송 상태를 관리한다.
6. **관리 화면:** 기존 어드민 섹션에 유형·기간·상태 필터와 발송 이력을 넣고 상세 모달에서 원본 미리보기, 준비 미완료 사유, 실패 재시도와 결과 불명 확인·정정 발송을 제공한다.
7. **배포 검증:** 모든 필수 SMTP 값을 제공하고 권한을 확인한 검증용 계정과 격리된 스테이징 DB에서 운영 이벤트 경로를 점검한다. 운영 DB의 스키마·연락처 준비와 환경변수를 검증한 뒤 운영 서버를 시작한다.

구현 단계와 실제 배포·발송 확인은 구분한다. 실제 SMTP 검증·운영 메일 발송 여부는 [운영 문서](../email-notification-operations.md)에 기록한다.

| `server/src/infrastructure/disclosures.ts`, `server/src/routes/admin.ts` | 공시 생성과 예약의 트랜잭션 연결, 수정·삭제 연동 |
| `server/src/application/record-monthly-dividend-service.ts` 및 저장 어댑터 | 저장 성공 후 준비 대상 표시. 주기 작업이 최종 누락 복구를 책임짐 |

계산식·상품 정책·기존 인쇄 확인서를 이메일 요구와 무관하게 개편하지 않는다. 서버와 클라이언트가 런타임 코드를 공유하지 않는 기존 구조를 유지하고 이메일 미리보기 DTO를 서버 계산 결과에 연결한다.

### 관리자 API 초안

모든 경로에 기존 관리자 인증을 적용한다. 변경 요청에는 기존 Origin 검사를 적용하며 반복 클릭은 요청 키와 DB 제약으로 중복 실행을 막는다.

| 경로 | 용도 |
| --- | --- |
| `GET /api/admin/notifications` | 종류·기간·상태별 목록, 페이지 단위 조회 |
| `GET /api/admin/notifications/:id` | 원본·준비 상태·개별 전송 결과 |
| `GET /api/admin/notifications/:id/preview` | 저장된 본문 미리보기. 자동 발송 부작용 없음 |
| `POST /api/admin/email-deliveries/:id/retry` | 명확한 실패의 동일 버전 재시도 |
| `POST /api/admin/email-deliveries/:id/resolve` | `UNKNOWN`의 외부 확인 근거와 결과 기록. 재시도 선택은 별도 명시 |
| `POST /api/admin/notifications/:id/corrections` | 정정 사유·새 입력·버전을 가진 안내 준비 |
| `POST /api/admin/notifications/:id/send` | 미리보기 완료 후 정정 안내 발송 요청. 정기 최초 발송에는 이 단계를 요구하지 않음 |

개인별 본문을 공통 이벤트 원본으로 노출하지 않는다. 정정 미리보기와 발송은 같은 고정된 입력 버전을 사용한다. 이미 `ACCEPTED`인 항목에 일반 재시도를 적용하지 않는다.

임시 테스트 옵션·미리보기·발송 경로는 제거한다. 운영 정정 발송·재시도 경로로 과거 TEST 이력을 전송하는 요청은 계속 거절한다.

### 운영 배포 시 확인할 사항

- 코드만으로 실제 DB의 적용 이력을 알 수 없다. 기존 스키마를 대조한 뒤 additive migration을 마련하고, 운영에서 `db push`나 스키마 초기화로 대체하지 않는다.
- 최초 배포 전 운영 DB의 연락처·스키마·대상 건수를 점검하고, 실제 발송 검증은 격리된 스테이징 DB에서 진행한다. 준비가 끝나면 필수 SMTP 값을 주입한 운영 서버를 시작한다. 최초 시작 시각을 누락 복구 경계로 저장하고 자동 전송한다.
- SMTP 비밀번호를 포함한 필수 설정은 서버 시작 전에 제공한다. 환경변수 형식 검증과 실제 발신 허용·인증·전송 성공은 별도로 확인한다.
- 발송 상태를 조회하는 목록은 전체 개인 본문을 한 번에 적재하지 않는다. 수신자·본문 데이터가 필요한 상세 조회만 별도로 수행한다.
- 현재 의향 상태·`updatedAt`에 의존하는 과거 계산의 한계는 유지된다. 발송 시점의 입력을 고정해 재시도 변동은 방지하지만, 기존 원장을 실제 계약·송금 원장으로 재해석하거나 과거 상태 이력을 복원하지 않는다.

## 7. 검증 계획

단위 테스트는 저장소 규칙에 따라 핵심 domain/application 로직에만 작성한다. `Given` / `When` / `Then`을 명시하고, 시계·DB·메일 공급자는 제어 가능한 대역으로 교체한다.

- 기간: KST 월·연도·분기 경계, 실행일 지연, 재시작 후 누락 기간, 최초 시작 이전 기간 제외.
- 수신 대상: 한 사용자 여러 의향, 완료·철회·거절 상태, 전액·부분 출금, 대상 조건에 따른 자동 발송, 연락처 오류, DataGSM 로그인 시 주소 갱신, 기존 의향서와의 주소 충돌, 상태 수정 시각과 주소 확인 시각 구분, 발송 결과 불명 항목의 주소 변경.
- 배분: 다음 달 적격, 해당 월 출금 FIFO, 사용자별 합산, 정책값, 적격 투자자의 0원 안내 발송·미입력 보류·비적격자 제외, 원 단위 합계·잔여액.
- 발송: 동일 이벤트 중복 예약, 일부 수신자만 실패, 일시·영구 오류, SMTP 인증·인증서 오류, SMTP 접수 후 로컬 기록 실패·최종 응답 유실 시 `UNKNOWN` 처리, claim 만료, 내용 고정, 정정 버전.
- 확인서 업무: 동일 분기 발급 중복, 최신 데이터 준비 실패, 발송 준비 지연 시 실제 기준 시각, 저장된 원본 생성 후 보유 내역이 달라져도 재시도에서 동일 데이터·본문 재사용.
- 시작 조건·운영 모드 경계: 필수 SMTP 값 누락 시 서버 시작 실패, 정상 시작 후 운영 작업의 상시 실행, TEST 원본의 운영 발송·재시도 거절, 운영 원장·정기 발송 키 불변, 요청자별 빈도 제한. HTTP 인증·Origin 경계는 격리된 통합 검증으로 확인한다.
- 임시 기능 제거: 삭제된 화면·API가 제공되지 않고 PRODUCTION 전용 claim, 구버전 TEST claim 거절, 과거 이력·UNKNOWN 확인 유지가 동작하는지 확인한다. 어드민 통합 패널과 상세 모달은 격리된 브라우저에서 확인한다.
- UI·메일 HTML·정적 콘텐츠에는 단위·스냅샷 테스트를 추가하지 않는다. 실제 메일 미리보기와 주요 메일 클라이언트 수동 확인으로 링크·한글·표·좁은 화면의 넘침·이미지 차단 시 가독성을 검증한다.
- 접근 제어, DB 제약·트랜잭션, 재시작 복구는 로컬 또는 격리된 통합 환경에서 확인한다.
- 변경 모듈의 가장 좁은 검증부터 실행한다. 전체 모듈 검증이 필요하면 `server`/`client`의 `npm run verify`, 프런트 배포 검증에는 `npm run build`를 추가한다.
- 테스트·타입 검사·린트·빌드 실패를 구분하고 이번 변경과의 관련성을 보고한다.

설계 시 기존 순수 배분 함수로 샘플 입력 2건을 검산했다. 이후 구현의 테스트·빌드 결과와 실제 환경에서 확인하지 못한 범위는 [운영 문서](../email-notification-operations.md)에 기록한다. 실제 메일은 보내지 않았다.

## 8. 완료 기준

1. 신규 공시 한 건을 저장하면 당시 잔액 보유자마다 한 건의 발송 항목이 생기고, 등록 요청은 SMTP 지연에 종속되지 않는다.
2. 매월 1일 데이터가 있으면 귀속월의 대상자에게 본인 금액을 전송하고, 데이터가 없으면 보류 후 입력 시 자동 처리한다. 0원은 정상 안내한다.
3. 1·4·7·10월 1일에는 최신 보유 내역 표가 본문에 포함되고, 개인 지급액 안내의 지연과 독립적으로 처리된다.
4. 각 투자자는 DataGSM 이메일로 안내받으며 별도 수신 주소·수신 설정 화면은 생기지 않는다.
5. 중복 작업 실행·재시작·부분 실패가 DB 항목을 중복 생성하지 않으며, SMTP 결과 불명은 무조건 재전송하지 않고 관리 화면에 표시된다.
6. 재시도는 저장된 기준월·계산액·보유 내역·본문을 유지한다. 정정은 새 버전으로 식별된다.
7. 다른 투자자의 이름·금액·이메일이 개인 메일이나 비인가 조회에 포함되지 않는다.
8. 변경 범위의 BDD 테스트와 필요한 lint·typecheck·build가 통과하고, 허가된 테스트 메일에서 HTML·텍스트·한글 표 표시를 확인한다.
9. 임시 테스트 발송·화면·샘플·전용 API가 코드에서 제거되고 TEST 대기 항목은 발송하지 않는다. 과거 이력·UNKNOWN 확인은 보존한다.
10. `/admin`의 발송 이력 패널에서 종류·상태·기간으로 조회하고 상세 모달에서 본문과 관리 작업을 확인한다. 발송 모드 선택·일정 안내 카드·불필요한 접기 메뉴는 제공하지 않는다.
11. 새 공시 이메일의 제목과 본문 제목은 공시 원문 제목을 사용하고 저장된 과거 발송 원본은 재작성하지 않는다.
12. SMTP 호스트·포트·TLS 방식·계정·비밀번호·발신자 중 하나라도 누락되거나 유효하지 않으면 서버 시작이 실패한다. 정상 시작한 서버는 운영 자동 발송을 실행한다.
