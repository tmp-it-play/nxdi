# 현금성 자산 반영 구현 명세

작성일: 2026-11-08 · 상태: 기능 배포·운영 초기화 완료, 임시 시드 제거

원화와 달러 현금성 자산을 기존 종목과 함께 표시하고, 총 평가액·등락률·보유 수익률·배당 배분·투자 접수 한도에 반영한다. 관리자는 현재 잔액을 직접 수정한다. 예금 등도 이 잔액에 포함하며, 최초 원금을 고정한 뒤 이후 잔액 변화와 환율 변화를 운용 성과에 포함하는 운영 방식을 사용한다.

## 1. 확정한 요구사항

| 항목 | 결정 |
| --- | --- |
| 관리 방식 | 관리자가 통화별 현재 잔액을 직접 입력·수정 |
| 지원 통화 | KRW, USD 두 개의 고정 항목 |
| 공개 표시 | 기존 보유 종목과 동일한 포트폴리오 목록에 통합 |
| 잔액 0 | 항목을 삭제하지 않고 목록에도 계속 표시 |
| 초기 원화 | 잔액 55,500원, 기준 원금 55,500원 |
| 초기 달러 | 잔액 0 USD, 기준 원금 0원 |
| 달러 최초 증가 | 첫 양수 입력부터 전액 손익에 포함. 원금을 새로 설정하지 않음 |
| 이후 수정 | 최초 원금을 유지하고 잔액 증감 전체를 손익에 반영 |
| 환율 | 기존 USD/KRW 환율 사용. 환율에 따른 평가액 변화도 전체 성과에 반영 |
| 원금 조정 | 별도 기능 없음. 취득환율을 직접 입력하는 기능도 없음 |

| 배당 배분 | 현금을 포함한 평가액 사용 |
| 투자 접수 한도 | 현금을 포함한 평가액의 50%를 기준으로 판단 |
| 반영 시작 | 배포 이후부터 반영. 과거 차트·확정 기록에 소급하지 않음 |
| 최초 반영일 | 현금 편입으로 오늘 등락률이 상승하는 것을 허용. 이를 상쇄하는 보정 없음 |
| 배포 초기화 | CD에서 없는 항목만 생성. 재배포 시 기존 잔액·원금 보존 |

추가 예치나 회수도 잔액 수정으로 입력하면 성과에 포함된다. 이는 이번에 선택한 계산 정책이다. 입출금 효과를 제거하는 수익률이나 자금 흐름 원장은 구현 범위에 포함하지 않는다.

## 3. 저장 구조

### 3.1 현금 모델

`PortfolioCashAsset` 모델과 `tb_portfolio_cash_assets` 테이블을 추가한다. 현금은 별도 모델에 저장하고 표시 단계에서 종목과 합친다. 실제 종목 테이블에 가상 티커를 넣으면 시세·배당 조회와 매매·삭제 기능에 섞이므로 사용하지 않는다.

| 필드 | 형태 | 의미 |
| --- | --- | --- |
| `currency` | 통화 키, KRW 또는 USD | 기본 키, 통화별 하나만 존재 |
| `balance` | `Decimal(18, 2)` | 현재 통화 잔액 |
| `initialBalance` | `Decimal(18, 2)` | 최초 통화 잔액, 수정 불가 |
| `initialCostBasisKrw` | `Decimal(18, 2)` | 최초 원화 기준 원금, 수정 불가 |
| `version` | 정수, 초기 0 | 오래된 화면의 덮어쓰기 방지 |
| `createdAt` | 생성 시각 | 최초 반영 시점 |
| `updatedAt` | 변경 시각 | 최신 잔액 갱신 시점 |

테이블·칼럼은 최근 Prisma 모델의 `tb_` 접두사와 `@map`을 사용하는 snake_case 규칙을 따른다. 통화는 두 값으로 제한한다. 원화 소수 입력은 거부하고 달러는 소수 둘째 자리까지 허용한다. 빈 문자열, 음수, 비정상 숫자, 저장 정밀도 초과 및 API에서 안전하게 표현할 수 없는 금액은 거부한다. 빈 입력을 0원으로 간주하지 않는다.

초기 데이터는 다음과 같다.

| 통화 | 현재 잔액 | 최초 잔액 | 원화 기준 원금 |
| --- | ---: | ---: | ---: |
| KRW | 55,500 | 55,500 | 55,500 |
| USD | 0 | 0 | 0 |

USD 원금은 영구적으로 0원이므로 첫 양수 잔액 입력 때 취득환율이나 원금을 새로 확정하지 않는다. 현재 환율만으로 평가하며, 달러 평가액 전부가 고정 원금 대비 손익에 포함된다.

### 3.2 평가 스냅샷

기존 `totalMarketValueKrw`, `costBasisKrw`에는 배포 후 현금까지 합산한 값을 저장한다. `PortfolioDailySnapshot`과 `PortfolioValuationObservation`에 현금 구성값을 nullable 필드로 추가한다.

- 원화 잔액: `cashBalanceKrw`
- 달러 잔액: `cashBalanceUsd`
- 현금 원화 평가액 합계: `cashMarketValueKrw`
- 현금 기준 원금 합계: `cashCostBasisKrw`

일별 확정값에는 대응하는 `close*` 필드도 둔다. 관측값에는 그 관측의 환산을 재현할 수 있도록 적용 환율도 기록한다. 기존 과거 행은 새 필드를 null로 유지하며, 현재 잔액이나 현재 환율을 대입하여 과거를 재계산하지 않는다.

## 4. 계산 기준

`S`는 현재 종목 평가액 합계, `K`는 원화 잔액, `U`는 달러 잔액, `R`은 현재 USD/KRW 환율, `B`는 현재 종목 매입원가 합계다.

```text
현금 평가액 C = K + U × R
총 평가액 V = S + C
현금 기준 원금 = 55,500원
전체 기준 원금 B_total = B + 55,500
현금 손익 = C - 55,500
전체 보유 손익 = V - B_total
전체 보유 수익률 = (V - B_total) / B_total
```

보유 종목의 원가가 누락되어 기존 수익률을 계산할 수 없는 경우에는 현금을 추가했다고 전체 수익률을 임의 계산하지 않는다. 보유 종목이 아예 없으면 종목 원가는 0으로 취급하여 현금만으로 계산한다. 분모가 0 이하이거나 필요한 기준 데이터가 없으면 비율을 `-`로 표시한다.

원화 현금은 55,500원을 기준으로 개별 보유 수익률을 계산할 수 있다. 달러 현금은 기준 원금이 0이므로 개별 수익률을 무한대나 0%로 표시하지 않는다. 달러의 손익 금액과 전체 포트폴리오 수익률에는 정상적으로 반영한다.

### 4.1 오늘 등락률

```text
오늘 등락률 = (현재 총 평가액 - 전일 확정 총 평가액) / 전일 확정 총 평가액
```

한국 시간의 바로 전날에 확정된 스냅샷을 사용한다. 현재 종목 수량에 전일 시세를 곱하는 기존 방식은 포트폴리오 전체 등락률에서 대체한다. 종목 상세의 종목별 등락률 계산은 유지한다.

이 방식에서는 현금 수정뿐 아니라 종목 보유 구성과 환율의 변화도 전체 평가액 변화로 나타난다. 매수·매도나 입출금을 중립화하는 보정을 하지 않는다. 전일 스냅샷이 없거나 확정되지 않았거나 전일 평가액이 0이면 `-`로 표시하고, 임의로 더 오래된 날짜나 현재 보유 수량 기준 비교로 대체하지 않는다.

처음 현금이 포함되는 날에도 전일의 기존 평가액과 그대로 비교한다. 예를 들어 종목 평가액이 전일과 오늘 모두 1,000,000원이고 55,500원 현금이 처음 포함되면 오늘 등락률은 5.55%다. 초기 편입분을 제거하거나 과거 종가를 보정하지 않는다.

### 4.2 차트 기록

현금 잔액 저장에 성공하면 같은 시점의 전체 평가액·전체 원가·예상 배당·현금 구성값을 당일 관측값으로 추가하고 당일 스냅샷을 갱신한다. 다음 정기 수집까지 기다리지 않는다. 정기 수집과 일별 확정도 같은 계산 함수를 사용한다.

이미 존재하는 평가액·수익률·배당수익률 차트에 이 값을 사용한다. 과거 스냅샷은 저장된 값 그대로 표시한다. 기능 도입 전후의 평가 범위가 달라지는 점은 지표의 계산 기준 설명에 짧게 명시한다.

### 4.3 배당과 투자 한도

- 포트폴리오 배당수익률은 기존 연 예상 배당금을 현금 포함 총 평가액으로 나눈다.
- 현금은 별도의 예상 금리 입력이 없으므로 예정 배당금 0으로 계산한다. 배당 데이터가 누락된 종목으로 취급하지 않는다.
- 잔액 증가는 운용 성과에 반영되지만, 월별 실배당 합계에 자동으로 가산하지 않는다. 월별 실배당은 기존 관리자 입력값을 사용한다.
- 월별 배당 배분은 해당 월의 확정 기준 평가액에 현금이 반영되어 있으면 이를 사용한다. 기존에 확정한 월별 기준 평가액과 배분 기록은 이 기능 배포만으로 변경하거나 재생성하지 않는다.
- 신규 투자 접수 판단은 현금 포함 총 평가액의 50%를 사용한다. 기존 분자의 산정 규칙과 초과 여부 판단 규칙은 유지한다.
- 투자 시뮬레이션도 현금 포함 구성비를 사용한다. 종목에 배정되지 않는 현금 비중을 별도로 표시하여 입력금액과 표시된 배분 금액이 일치하도록 한다. 현금 몫에 예상 이자나 배당을 임의 부여하지 않는다.

## 5. 관리자 입력과 서버 처리

### 5.1 화면

운영 포트폴리오 목록에서 현금은 이름·현재 잔액·원화 평가액을 표시한다. 관리 화면에서는 통화별 현금 행에 현재 잔액이 실제 값으로 채워진 입력란과 저장 버튼을 둔다.

```text
원화 현금  [ 55,500 ] 원    [저장]
달러 현금  [   0.00 ] USD   [저장]
```

현재 금액은 placeholder가 아니라 수정 가능한 입력값이다. placeholder는 빈 입력의 예시에만 사용한다. Enter로도 저장하며, 입력 중인 숫자가 매번 서버에 저장되지는 않는다. 저장 중에는 중복 제출을 막고, 성공 후 현재 잔액·전체 평가액·지표를 갱신한다. 실패 시 입력을 보존하고 이유를 표시한다.

기존 `FormattedNumberInput`과 `ApiMutationForm`을 활용한다. 종목 등록·매수·매도·증여 폼을 현금 관리에 노출하지 않는다. 현금에는 삭제 버튼을 두지 않는다.

### 5.2 API

기존 관리자 폼 처리 방식에 맞춰 `POST /api/admin/portfolio/cash`를 추가한다.

```text
currency: KRW | USD
balance: 정규화된 금액 문자열
expectedVersion: 화면에서 읽은 버전
```

관리자 인증과 기존 요청 보호 규칙을 적용한다. 원금·통화 변경·생성·삭제는 이 엔드포인트로 받지 않는다. 성공 응답은 기존 관리자 폼 응답 규격을 따른다. 충돌은 최신값을 다시 읽어 수정하도록 안내한다.

처리 순서는 검증, 사용할 환율 확보, DB 트랜잭션 진입, 버전 확인, 잔액 갱신, 현재 자산 집계, 당일 스냅샷·관측 저장, 커밋이다. 같은 금액 재저장은 무변경 성공으로 처리하고 관측값을 불필요하게 추가하지 않는다.

잔액만 저장되고 차트 기록이 실패하는 부분 성공은 허용하지 않는다. 스냅샷 쓰기·일별 확정·현금 저장의 잠금 순서를 통일한다. 정기 수집이 오래된 현금값으로 최신 스냅샷을 덮어쓰지 않도록 잠금 이후 현재 잔액을 읽어 집계한다. 시각은 주입 가능한 의존성으로 두고 한국 시간의 스냅샷 날짜를 사용한다.

현금 수정 때 전체 종목 시세를 새로 요청하지 않는다. 기존 저장 시세와 검증된 현재 환율로 계산한다. 필요한 환율을 확보할 수 없으면 저장과 스냅샷 기록을 모두 실패 처리하여 서로 다른 기준값이 남지 않게 한다.

## 6. 조회와 표시의 일관성

`PortfolioOverview`에 `cashAssets`, `securitiesMarketValueKrw`, `cashMarketValueKrw`를 추가한다. 기존 `holdings`는 실제 종목만 담고, `totalMarketValueKrw`는 두 자산군을 합산한다. 클라이언트는 표시용 판별 타입으로 두 종류의 행을 합친다.

- 공개 목록은 평가액 순으로 종목과 현금을 함께 보여주며 0원 현금도 필터링하지 않는다.
- 현금 행에는 통화 잔액과 원화 평가액을 표시한다. 주식 수량 단위, 거래소, 종목 상세 링크를 붙이지 않는다.
- 구성비 차트에는 양수 현금 두 항목을 각각 포함한다. 현금은 종목의 ‘기타’ 묶음과 구분한다. 0원은 목록에 유지하되 0 크기의 차트 조각을 억지로 만들지 않는다.
- 현금 자체의 외부 시세 차트를 요청하지 않는다. 기존 전체 평가·수익률 차트가 현금 변화까지 포함한다.
- 종목 개수와 자산 개수를 구분한다. 현금이 두 개 추가되었다고 실제 보유 종목 수를 늘리지 않는다.
- `fetchedAt`은 종목과 현금의 변경 시점을 모두 고려한다. 환율의 출처·시각은 기존 방식으로 별도 제공한다.
- 보유확인서의 총액을 종목만 다시 합산하지 않도록 수정한다. 현금 행, 구성비, 문서 지문·페이지 분할도 같은 자산 목록을 사용한다.
- 새로 준비하는 보유확인서 이메일에도 현금 내역을 포함한다. 기존 준비·발송 완료 이메일의 저장 내용은 변경하지 않는다.
- 구버전 클라이언트를 위한 서버 응답은 필드 추가 중심으로 변경한다. 기존 필드 제거 없이 서버와 클라이언트 배포 순서를 맞춘다.

## 7. 최초 CD 임시 시드 실행 및 제거

2026-11-08 첫 기능 배포(`068deab`)의 서버 CD가 성공했고, 운영 API에서 원화 잔액·최초 원금 55,500원과 달러 잔액·최초 원금 0원을 확인했다. 임시 시드는 마이그레이션 다음에 Prisma `createMany`의 `skipDuplicates`로 없는 통화만 생성했다. 기존 행의 잔액·원금·버전·수정 시각은 변경하지 않았으며, 격리된 DB에서 재실행 시 보존을 검증했다.

초기화 확인 후 임시 시드 스크립트, `db:seed-cash` npm 명령, Docker 복사 단계, 배포 시드 실행 단계를 제거했다. 이후 CD에서는 마이그레이션만 실행하며 이미 생성된 현금 항목과 최초 원금은 그대로 유지한다. 잔액 수정이나 재배포로 초기 금액을 다시 덮어쓰지 않는다.

임시 시드를 제거한 이후 완전히 새로운 DB를 설치한다면 현금 항목의 초기화는 별도로 수행해야 한다. 이 경우에도 기존 운영 DB의 현금 항목을 삭제하거나 재초기화하지 않는다. 스키마 마이그레이션에는 초기 잔액을 넣지 않는다.

## 8. 기존 정책 문서와 기록 보존

상품 설명·배당 정책 문서와 `server/src/domain/document-policy.ts`의 버전·해시는 이번 구현에서 변경하지 않는다. 현금의 평가·배당 배분·접수 한도 반영은 합의한 애플리케이션 동작에 한정한다. 기존 의향서 동의 기록, 월별 배당 기준값, 준비·발송 완료 알림도 이 기능 배포만으로 다시 쓰지 않는다.

## 9. 검증 계획

핵심 도메인·서비스 로직만 단위 테스트를 추가한다. 새 테스트는 `describe("Given ...")`, 내부 `describe("When ...")`, `it("Then ...")` 형태를 사용하고 DB·환율·시각을 통제된 테스트 대역으로 대체한다.

| 검증 대상 | 기대 결과 |
| --- | --- |
| 초기 생성 | KRW 55,500/55,500, USD 0/0 생성 |
| 시드 재실행 | 수정된 잔액·최초 원금·버전·시각 보존 |
| 통화 일부 존재 | 없는 항목만 생성 |
| 원화 55,500 → 60,000 | 현금 손익 +4,500원, 고정 원금 유지 |
| 달러 0 → 100, 환율 1,400 | 평가액·전체 손익 +140,000원, USD 원금은 계속 0 |
| 달러 100 유지, 환율 1,400 → 1,500 | 전체 평가액·손익 +10,000원 |
| 잔액 0으로 수정 | 행·원금 유지, 손익·집계 갱신 |
| 현금만 보유 | 전체 평가액·보유 수익률·배당수익률 계산 가능 |
| 종목 원가 누락 | 전체 보유 수익률을 임의 계산하지 않음 |
| 전일 확정 종목 평가 1,000,000, 당일 시드 편입 | 다른 변화가 없으면 오늘 등락률 5.55% |
| 전일 확정값 없음 또는 0 | 오늘 등락률 계산 불가, 무한대·가짜 0% 방지 |
| 잔액 저장 | 스냅샷·장중 관측에 즉시 반영 |
| 스냅샷 실패 | 잔액 갱신도 롤백 |
| 동시 수정·정기 수집 | 버전 충돌 감지, 오래된 값으로 덮어쓰기 방지 |
| 같은 금액 재저장 | 잔액·관측에 불필요한 변경 없음 |
| 과거 데이터 | 기존 스냅샷·확정 월별 기준·발송 완료 내용 보존 |
| 배당·한도·시뮬레이션 | 같은 현금 포함 평가액 사용, 현금은 배당 누락 아님 |

UI·문서·설정·단순 DTO·프레임워크 배선에 대한 새 단위 테스트나 스냅샷 테스트는 추가하지 않는다. 다음은 적절한 수동 확인과 실행 검증으로 확인한다.

- 입력값 수정, Enter·저장 버튼, 오류 후 입력 보존, 0원 행 유지, 모바일 배치.
- 공개 목록·차트·관리 화면·보유확인서·이메일의 내역 합과 총액 일치.
- 격리된 DB에서 마이그레이션과 시드 2회 실행, 잔액 수정 후 재실행 시 보존.
- 운영 의존성만 설치한 이미지에서 시드 실행 가능 여부.
- 관리자 권한 없는 잔액 수정 요청 거부와 금액·버전 검증.
- 기존 정책 문서·버전·해시에 변경이 없는지 확인.

구현 중에는 변경 모듈의 가장 좁은 검증부터 실행한다. 전체 완료 시 서버와 클라이언트에서 각각 `npm run verify`, 클라이언트에서 `npm run build`를 실행하고 변경한 배포 셸에는 `bash -n`을 적용한다. API 변경의 최종 검토에는 저장소 보안 체크리스트를 적용한다. 테스트·타입 검사·린트·빌드 실패는 구분하여 보고한다.

## 10. 구현 순서와 완료 기준

1. 현금 모델·마이그레이션·시드와 CD 연결을 추가한다.
2. 현금 평가·고정 원금·전체 성과 계산과 서비스 테스트를 구현한다.
3. 잔액 변경과 스냅샷 저장의 일관성을 구현한다.
4. 조회 모델·배당·한도·시뮬레이션을 같은 평가값에 연결한다.
5. 통합 자산 목록·현금 입력·차트·확인서·이메일을 반영한다.
6. 기존 정책 문서·동의 기록을 보존하고 전체 검증을 완료한다.

완료 시 관리자가 현금 잔액을 저장하면 현재 총액과 지표가 재계산되고 당일 차트 기록에도 반영되어야 한다. 원화 55,500원·달러 0원의 고정 원금은 재배포와 모든 잔액 수정 후에도 유지되어야 한다. 0원 현금 항목은 계속 존재하고 공개 목록에서도 확인할 수 있어야 한다.
